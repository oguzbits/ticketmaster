# 0009: Row-level security as a second ownership layer

- Status: accepted
- Date: 2026-11-15

## Context and problem statement

Invariant 2 says every query on user-owned data filters by ownership on the server and that
PostgreSQL row-level security is the second layer. Until now the app connected as `app`, a
superuser, so no policy could apply. Several production paths also read `bookings` across users on
purpose (seat availability in a hold, sales counts of an organizer, the seat-change publish, the
expiry job, the ticket effects of the worker, the demo cleanup), and `lockOwnBooking` must answer
403, not 404, for a booking of someone else. How does the database back the customer paths without
breaking those?

## Decision drivers

- A customer query that forgets its ownership filter must not return or change a foreign row.
- The cross-user paths and the worker stay unchanged, and so does the 403 for a foreign booking.
- Works through PgBouncer in transaction mode ([ADR 0005](0005-pgbouncer-transaction-mode.md)), so
  no session state.
- Migrations stay generated by drizzle-kit; hand-written SQL only in a custom migration.

## Considered options

1. A runtime role without superuser and ownership, policies that restrict rows only while a
   transaction sets `app.scope = 'user'`.
2. The same role, policies that fail closed: no scope means no rows, every path sets a scope.
3. Policies in the drizzle schema with `pgPolicy`.
4. A second role with `BYPASSRLS` for the cross-user paths and two connection pools.
5. `SECURITY DEFINER` views for the cross-user aggregates.

## Decision outcome

Chosen: option 1. `app_runtime` (created by the migration job, password from `DATABASE_URL`) is the
login of API and worker; `app` owns the tables and runs migrations. The policies on `bookings` and
`booking_transitions` hide foreign rows (and refuse writes for them) only while the transaction set
`app.scope = 'user'` and `app.user_id`. `withOwner(tx, userId, run)` sets both with
`set_config(..., true)` and sets the scope back to `system` afterwards. Inside the user scope a
missing `app.user_id` sees nothing. Customer paths opt in: the booking list and the transitions
that pay and cancel store.

### Consequences

- Good: a forgotten `user_id` filter in the list, or a transition written for a foreign booking,
  fails at the database. A bug of that kind needs two mistakes.
- Good: nothing changes for the cross-user paths, the worker or the 403 of a foreign booking.
- Bad: protection is opt-in. A customer path that does not call `withOwner` has no database layer.
  The ticket download and `claimPaymentKey` are such paths: the first needs the foreign row for its
  403, the second would turn a foreign update into a silent no-op under the policy.
- Bad: the scope is a session variable, so code that can run arbitrary SQL can set it. The layer
  guards against a forgotten filter, not against SQL injection.
- Bad: the owner login needs `CREATEROLE` wherever the migration job runs.

## Pros and cons of the options

### Option 1: opt-in user scope

- Good: small change, no behavior change outside the opted-in statements.
- Bad: a forgotten opt-in is not caught.

### Option 2: fail closed

- Good: a path that forgets the scope sees nothing.
- Bad: about twenty transaction sites (worker, expiry, simulator, organizer, outbox) would need a
  scope, and a user-scoped read turns the 403 for a foreign booking into a 404.

### Option 3: `pgPolicy` in the schema

- Good: policies live next to the tables.
- Bad: no support for the session settings used here, and the grants still need SQL.

### Option 4: two roles and two pools

- Good: no session variable to set.
- Bad: the hold transaction needs both views (cross-user availability, own insert), which two
  pools cannot give inside one transaction.

### Option 5: `SECURITY DEFINER` views

- Good: aggregates keep working under a strict policy.
- Bad: more objects to maintain, and every cross-user query moves behind a view.
